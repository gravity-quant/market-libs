<threat_model>
This plan adds the public dispatch surface (methods, shims, re-exports) over the Plan 01 pure layer. It introduces NO new auth flow, NO secret handling, NO mutation, NO new transport, and NO new dependency — every method delegates to the UNCHANGED Phase-20 `_request` layer.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| caller → client surface | Filter kwargs cross here into the builders; no injection risk (kwargs are serialized as query params by httpx, not interpolated) |
| client → market-data API | Authenticated GET; Bearer injection + `_ensure_token` handled by the UNCHANGED `_request`/`_ensure_token` layer |
| market-data API → client | Untrusted response payloads flow through the Plan 01 parsers/`from_api` (tolerant, never raise) |

| Threat ID | Category | Component | Disposition | Mitigation Plan |

| T-22-04 | Information Disclosure | filter kwargs (`q`, `prefix`) in the request URL / structured logs | accept | Filter values are caller-supplied query params, not credentials; the Phase-20 `RedactingFilter` already redacts Bearer/secret material (unchanged). No new logging is added by the dispatch surface. |
| T-22-05 | Spoofing / Elevation | the 5 authenticated methods on Client/AsyncClient | mitigate | Methods dispatch specs with `authenticated=True` (Plan 01) → existing `_request` injects the Bearer and refreshes via `_ensure_token`; no method bypasses auth, and no new auth code is written here. |
| T-22-06 | Tampering / DoS | response handling in the 5 methods | mitigate | Methods return whatever the Plan 01 parsers produce — `from_api` tolerance + 204/null guards mean a hostile/partial payload yields typed zeros or `[]`, never an unhandled raise. |

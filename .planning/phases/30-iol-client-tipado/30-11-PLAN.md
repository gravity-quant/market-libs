approach_decision:
  id: "AD-30-11-01"
  question: >
    Close the second-renderer bypass by analysing every function in the driver to decide whether it
    is a renderer, or by flagging the *call site* where a handler-bound exception is handed to a
    non-sanctioned callee?
  chosen: "both, split by role — call-site flagging inside handlers (primary), plus a narrowed, annotation-gated renderer census (secondary)"
  reversibility: "two-way"
  rationale: >
    A whole-file "is this function a renderer?" analysis is the shape 30-REVIEW.md's WR-02 snippet
    proposes, and it does not survive contact with the driver: applied verbatim it returns an empty
    list, because `_redacted_exc`'s own body contains no `repr`/`str` call and no `.message`/`.args`
    read — it uses `getattr`, `type(exc).__name__` and `IOLDecodeError` attribute reads — so the
    assertion `renderers == ["_redacted_exc"]` fails on a compliant driver. Worse, any predicate
    loose enough to catch `_redacted_exc` by generic parameter-attribute-read also catches roughly
    every probe in the file, since they all read attributes off their `client` parameter.
    The leak, however, must flow through an `ast.ExceptHandler` at some point — that is the only
    place the driver ever obtains an exception object. Flagging the bound name being handed to any
    callee outside a short sanctioned allow-list closes the "second renderer under another name"
    bypass at the point where it is decidable, without analysing the callee at all. The renderer
    census then only has to catch a duplicate of `_redacted_exc` itself (async, nested, or
    renamed-and-annotated), which an annotation-gated predicate does cleanly. Reversible: the whole
    change is inside one offline test file; no driver source, no package source, no dependency.

<objective>
Make the AST regression lock added by 30-09 actually enforce what 30-09-SUMMARY.md claims it
enforces.

The lock is the artifact that keeps the CR-01/CR-02 leak class closed after this phase ends. As
shipped it covers three shapes out of eleven that a fresh code review enumerated, and its companion
renderer-count test can be walked past three different ways. No leak exists in `main_iol.py` today
— this is a durability gap in the lock, not a live disclosure — but a lock that does not fail on
the vulnerability class it names is a lock the next author deletes or, worse, trusts.

Purpose: `IOLAPIError.message` is literally `resp.text`. `append_finding(actual=exc.message)` is a
one-token edit away from every one of the 32 sites 30-09 just swept, and the lock as shipped is
blind to it. Same for a helper named anything other than `_redacted_exc`.

Output: a widened `_raw_exception_renders`, a new source-string renderer census replacing the
name-matching count test, an extended positive control with one planted occurrence per new shape,
and an unchanged negative control. Test surface only — no driver code, no package code.
</objective>

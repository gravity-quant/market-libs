  <name>Task 1: Decide the nullability declaration for the nine under-determined health-feed fields</name>
  <decision>
Which health-feed fields are declared `str | None` versus `str`?

The two error fields are already locked by CONTEXT D-01 as `str | None`
(`FeedIngestor.last_error`, `FeedPipeline.last_write_error`). The question is the other seven,
plus whether the two error fields' non-null type is really `str`.
  </decision>
  <context>
`.planning/verification/schemas/market-data-client/get-health-feed.json` was captured on
2026-07-31 from a **connected ingestor with an open market**. It is a single state. Every
timestamp came back a string and both error fields came back `null`, so the capture cannot
distinguish "never null" from "not null right now".

The tradeoff is asymmetric and runs against tolerance. `_decode.walk_field`'s union-with-None
branch returns `None` **without emitting a divergence record**. So:

- Declaring a field `str` when the wire can send `null` → Phase 33's strict driver run RAISES.
  Loud, immediate, and corrected in that cycle. This is the designed outcome, not a break.
- Declaring a field `str | None` when the wire never sends `null` → nothing happens, ever. The
  Optional silently absorbs a genuine null if one later appears, and the divergence census that
  this whole milestone exists to produce under-counts by exactly that field.

RESEARCH § Open Question 1 recommends option A while its own closing sentence argues the
tradeoff "argues for restraint" — the two halves are in tension, which is why this is a
checkpoint rather than a planner decision. Phase 29's ratified sizing floor
(`market-data-client >= 50` divergences) is a **floor**, and an over-declared Optional is one of
the ways a real census could come in under it while reading clean.

Undo cost: changing a declaration later is a one-line edit, but once these ship in Phase 34,
narrowing `str | None` back to `str` is a source-breaking type change for consumers. More
importantly, the missed observation window between now and the correction cannot be recovered.
  </context>
  <options>
    <option id="option-a">
      <name>RESEARCH recommendation — the two locked error fields plus the five market-session fields are `str | None`</name>
      <pros>A closed or disabled market plausibly has no session times, so `next_transition`, `session_open`, `session_close`, `last_business_day` and `reason` are the most likely nulls. Reduces the chance that Phase 33's first strict run raises on a benign state and stalls the sweep.</pros>
      <cons>Five Optionals declared on inference, not evidence — the capture shows `enabled: true` with a populated `reason`. Each one is a field whose future null becomes invisible. Directly in tension with the milestone's core value.</cons>
    </option>
    <option id="option-b">
      <name>Restraint — ONLY the two CONTEXT-locked error fields are `str | None`; every other field is declared per the capture</name>
      <pros>Declares nothing that was not observed. Every wrong guess surfaces in Phase 33 as a loud `wrong_type` divergence, which is the designed outcome and is directly comparable against the ratified `>= 50` floor. Zero fields go silently unobservable.</pros>
      <cons>Phase 33's strict driver run may raise on a legitimately-null field and need an in-cycle fix before the sweep continues — one extra correction round, on a field this phase deliberately chose not to guess about.</cons>
    </option>
    <option id="option-c">
      <name>Maximal tolerance — all nine under-determined fields are `str | None`</name>
      <pros>Phase 33's strict run cannot raise on any of them.</pros>
      <cons>Nine fields become permanently divergence-blind. RESEARCH argues against this explicitly. Listed for completeness, not recommended.</cons>
    </option>
  </options>

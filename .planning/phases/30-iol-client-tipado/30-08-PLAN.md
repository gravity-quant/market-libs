  chosen: "redact at the emitter"

  rationale: >
    A sink-side scrubber would have to guess which substrings of an arbitrary `actual` string are
    wire values, because by the time the string reaches append_finding the type information that
    would let it decide is gone. That is a lossy heuristic guarding six drivers, and it would make
    every driver's finding text depend on a shared redaction policy no driver can see. The emitter,
    by contrast, still holds the exception object and can name exactly the two safe facts —
    the exception class and its status code — without inspecting any string. This is the same
    discipline exceptions.py already ratified for IOLDecodeError (T-29-36: "tipos y rutas, jamás un
    valor del wire") and that 30-06 ratified for the drift probes (T-30-06-01), applied to the one
    code path in this driver that still violated it. Reversible: the change is one string expression
    plus a docstring paragraph in one private driver function, guarded by a new test; no package
    source, no committed baseline, no published API, no shared harness module.

<objective>
Close the BLOCKER escalated by 30-VERIFICATION.md (2026-08-21) and 30-REVIEW.md CR-01: this
phase's own verification harness writes the full upstream error response body into a
version-controlled file.

`_capture_raw_wire` catches every capture failure and reports the exception's full
representation as the finding's `actual`. That exception is built by `_core.raise_for_response`,
which passes `resp.text` — the entire error body — into `IOLAPIError.__init__`, which stores it
in `Exception.args`. `verification.findings.append_finding` performs no redaction (only
`safe_print` redacts, and only for stdout). The body therefore lands verbatim in
`.planning/verification/iol-client-findings.md`, which `git ls-files` confirms is tracked. On an
authenticated run against a real brokerage API, an error body plausibly carries account and
instrument identifiers, and once committed the exposure is permanent and distributed on push.

Three statements this project already ratified are false about that code path today: the
function's own docstring at `main_iol.py:264-265` ("el body crudo alimenta `schema_of` y nada
más. Ningún argumento de `append_finding` recibe un body"), `exceptions.py`'s T-29-36 invariant
("tipos y rutas, **jamás** un valor del wire"), and CLAUDE.md's constraint against exposing
sensitive data in reports. The committed findings artifact happens to be clean today; the code
path is live and fires on the next capture failure.

Purpose: make the docstring true. Two facts are enough to diagnose a failed capture — which
exception class, and what status code — and neither is a wire value. Everything else the
exception knows belongs to the caller, not to a durable report.

Secondary: close the two WARNING-level test-quality gaps the same verification recorded, both
in the same test file. WR-01's test cannot fail for the reason it claims; WR-02's test pins a
known, separate, still-open defect as a permanent invariant.

Output: `main_iol.py` with a redacted failure path and a docstring that states the failure-path
rule explicitly, and `verification/test_main_iol_raw_wire_drift.py` with a marker-leak
regression section plus the two strengthened tests.
</objective>

<objective>
Make the verbatim-copy contract enforceable. Without a gate, five copies of a
module in a repository with no shared code between packages will diverge, and
the divergence will be discovered by a bug rather than by CI.

The gate must survive two traps. First, a naive byte comparison fails
immediately: near-duplicate blocks in this repo already differ by a couple of
lines, and one of the five filter bodies legitimately carries an extra
package-specific block. Second, the natural home for a cross-package check is a
directory that has never executed in CI, because the tests job passes an
explicit package path that overrides the configured test paths.

Purpose: DEC-01 requires the helper to exist copied verbatim with an intactness
check. This plan is that check, plus the written record of the one package that
is out of scope.
Output: `tools/check_decode_intactness.py`, a new step in the lint job, and
`29-WALLETS-EXEMPTION.md`.

Decisions implemented: D-02 (intactness by hash plus ban-list grep over the five
copies, with `wallets-client` carrying a documented exemption rather than a
bootstrap), D-05 (the filter fix's scan region is part of what the gate keeps
identical across copies).
</objective>

The module docstring states the contract in full, because these rules are the
only sanctioned place to record a legitimate difference between copies:

Check A — decode-helper intactness. Read all five `_decode.py` copies. Apply the
normalization, in this order, and hash the result:
  1. Drop the module docstring entirely.
  2. Replace every occurrence of the package's own import name with a fixed
     placeholder token.
  3. Replace the string literal passed to the logger factory with a placeholder.
  4. Replace the two ContextVar name string literals with placeholders.
  5. Replace the whole `POLICY` assignment statement with a placeholder.
  6. Replace the decode-error import line and every reference to the decode-error
     class name with placeholders.
  7. Strip trailing whitespace per line and normalize the trailing newline.
Require that the five normalized bodies reduce to exactly one hash. On failure,
print which copies disagree and a unified diff of the first disagreeing pair, so
the operator sees the drift rather than only a hash mismatch.

Check B — filter scan-region intactness. Read all five `_logging.py` copies,
extract the text between the two marker comment lines that delimit the generic
scan region, apply normalization steps 2 and 7, and require exactly one hash
across the five. Fail with a clear message if a marker pair is missing from any
copy. This is what keeps matriz's package-specific pre-scan block outside the
comparison by construction; do not hardcode a second expected hash for it.

Check C — ban list. Grep every file under the package source trees for two
call-shaped constructs that would let a copy quietly stop behaving like a copy.
Match the constructs as calls or keyword arguments, not as bare names, and say so
in a comment: the decode module's own docstring legitimately discusses strictness
in prose, and a name-shaped pattern would fail the build on a docstring. The two
banned constructs are the disabled-strictness keyword argument
`strict=False`<!-- planner-discipline-allow: strict=False --> and any call to the
third-party field helper `msgspec.field(`<!-- planner-discipline-allow: msgspec.field( -->.
Report every match with its file and line.

Check D — package roster. Hold the five in-scope package directories in an
explicit constant, and hold `wallets-client` in a second constant named as an
exemption with a one-line reason and the phase that resolves it. Fail if a
package source tree that is in the in-scope list has no decode module, and fail
if the exempt package has acquired one without the roster being updated. The
roster is the machine-visible record of the copy topology; keep it beside a
comment pointing at `29-WALLETS-EXEMPTION.md`.

Print a one-line summary per check on success so a green CI log still shows what
was verified.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| contributor edit → five copies | Any future change can touch one copy and not the other four; the gate is the only thing between that and a silent behaviour split. |
| CI configuration → gate effectiveness | A gate placed in a job or directory that does not execute is indistinguishable from no gate. |
| checker script → repository source | The script reads every package source tree; it must not execute any of it. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-29-47 | Tampering | one decode copy drifting from the other four | mitigate | Normalize-then-hash over all five with the rules written in the checker docstring; drift injection is an acceptance criterion, so the gate is proven to fail red before it is trusted. |
| T-29-48 | Tampering | the filter fix drifting between copies | mitigate | Marker-delimited region hashed across all five, so the one legitimate package-specific block is outside the comparison rather than encoded as a brittle second hash. |
| T-29-49 | Tampering | a copy silently opting out via a disabled-strictness argument or a third-party field helper | mitigate | Call-shaped and keyword-shaped ban-list grep over every package source tree, reporting file and line. |
| T-29-50 | Repudiation | an inert gate believed to be active | mitigate | The step is added to the lint job, which executes on every push and pull request; the acceptance criteria assert its presence by parsing the workflow rather than by reading it. |
| T-29-51 | Tampering | the exempt package quietly acquiring a copy without the roster being updated | mitigate | Check D fails if the exempt package acquires a decode module, and the exemption document and the roster constant reference each other. |
| T-29-52 | Elevation of Privilege | the checker importing and executing package source | accept | The checker reads files as text and never imports a package module, so no package import-time side effect runs inside the gate. Low risk; the read-only behaviour is visible in the source. |
</threat_model>

<objective>
Implementar el fix in-cycle de IOL-07 — `grant_type=refresh_token` con fallback a password grant — en ambas superficies del cliente IOL (`client.py` sync + `aio.py` async), respetando convención dual espejada de CLAUDE.md y los decisiones lockeadas D-IOL-8/9/10. El plan agrega un singleton `_refresh_token: str | None` y un helper privado `_refresh()` / `_refresh_unlocked()` por surface, modifica `login()`/`_login_unlocked()` para capturar el `refresh_token` del payload OAuth, modifica `configure()` para resetearlo, y modifica `_ensure_token()` para intentar refresh antes de fallback a password. Cierra con 4 tests mockeados sync + 4 mirror async en la nueva sección `# ------ Regressions ------` por surface (D-IOL-12). Es la DRY foundation de Phase 3: el driver del Plan 03-02 verifica el fix in-vivo en `probe_refresh_token` leyendo `iol_client.client._refresh_token`.

Purpose: Sin el fix de IOL-07 el cliente IOL re-dispara password grant en cada 15-min expiry, consumiendo intentos de auth contra `api.invertironline.com` con riesgo de lockout silencioso (CONCERNS.md L25-29). Este plan elimina el riesgo en el código y deja regresiones que detectarían cualquier regresión futura. Mirror dual obligatorio por CLAUDE.md ("Dual sync/async espejado por convención").

Output: `client.py` + `aio.py` con `_refresh_token` + `_refresh()`/`_refresh_unlocked()` + `_ensure_token()` con fallback; `test_client.py` + `test_async_client.py` con sección `# ------ Regressions ------` poblada con 4 tests por surface (8 total); mypy strict + ruff verdes; suite pre-existente sin regresiones.
</objective>

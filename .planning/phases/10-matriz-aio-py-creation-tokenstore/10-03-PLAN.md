## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Sync `Client._ensure_token` → `state.token_store` | Within-instance API; trusted caller; state field write through TokenStore.get_sync() |
| Async `AsyncClient._aensure_token` → `state.token_store` | Within-instance async API; trusted caller; state field write through TokenStore.get_async() |

| T-10-03-01 | Information Disclosure | ws_client daemon thread token leak via traceback | mitigate | The daemon thread reads `state.token_store.get_sync().value`. If the daemon thread crashes with an unhandled exception, the traceback could include `state.token` in `locals()`. Mitigation: existing `_logging.RedactingFilter` covers `X-Auth-Token` patterns in log records (LOG-02). The traceback path through the `ws_client` daemon does NOT format `state.token` into a log record by default (line 157 inserts the token into `header`, not into a log message). Verified by: `grep -n "logger\..*token" packages/matriz-client/src/matriz_client/ws_client.py` returns 0 matches. |
| T-10-03-02 | Information Disclosure | TokenStore shared between sync Client and ws_client daemon thread | mitigate | The cross-leak sentinel test (Phase 7 D-10, `verification/test_sync_async_isolation.py`) ensures sync default Client's `_state` is SEPARATE from async default Client's `_state` — both have their own `state.token_store`. The ws_client daemon thread reads from the SYNC default Client's state (per `_rest._get_default()` import in `ws_client.py`), so it shares with the sync REST surface but NOT with the async REST surface. This is the intended 3-way contract. Plan 10-04 extends the cross-leak sentinel for matriz async. |
| T-10-03-03 | Tampering | Credential leak via concurrent state mutation | mitigate | `_state.token_store` field is set under `_state_lock` (inside TokenStore implementation, transparently). The lazy-init pattern `if state.token_store is None: state.token_store = build_token_store(...)` has a race window: two threads could both observe `None` and both build a store. Mitigation: the second store's refresh would still go through the SAME `state.http_client` and use the SAME credentials; the only impact is one redundant TokenStore construction (negligible — no extra auth-server hit because both stores have the same TTL+refresh policy and only one stays referenced by `state`). For 100% atomicity, future v1.2 could wrap the lazy-init in `_state_lock` from the OUTSIDE; for v1.1 accept-and-document. |
| T-10-03-04 | Tampering | `password is not None` → `state.token_store = None` reset path | mitigate | When `configure(password=...)` is called with new credentials, both `state.token` and `state.token_store` MUST be reset. If we reset only `state.token` (forgetting `state.token_store`), the old TokenStore would continue serving the cached OLD token because its TTL has not expired. This is a credential-update bypass vulnerability. Mitigation: explicit reset of `state.token_store = None` in BOTH sync `Client.configure` path AND module-level `configure(password=...)`. Verified by acceptance grep that the reset lines exist. ASVS V3.2.2 (authentication credentials rotation). |

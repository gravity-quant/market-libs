<objective>
Fix `GET /calendar` parsing offline, before anything destructive runs. `parse_calendar_response`
iterates the response body as a list, but develop returns the object envelope
`{config, coverage, days[], market}` — already captured verbatim in the committed baseline
`.planning/verification/schemas/market-data-client/get-calendar.json`, and declared
`{"type":"object"}` by the live OpenAPI. Iterating a dict yields its **keys**, so today
`get_calendar()` produces `CalendarDay` rows built from the strings `"config"`, `"coverage"`,
`"days"`, `"market"` — and `CalendarDay`'s declared fields (`date`, `marketId`,
`isBusinessDay`) do not exist on the wire at all.

Purpose: this is a **hard prerequisite of ROADMAP criterion 2** (D-12). `GET /calendar` is the
only read that can confirm an `add_holidays` landed, so the holiday create→verify→revert
cycle of plan 27-04 cannot be verified without it.
Output: a corrected shared parser, a `CalendarDay` reconciled against the real wire, and
mirrored sync/async regression coverage.

Per D-13 this is treated as a **minor, non-breaking** change: `parse_calendar_response` has
always been broken, so no consumer could ever have read a populated `CalendarDay`. If the live
evidence in plan 27-05 contradicts that, escalate the major-vs-minor question **before**
Phase 28 rather than deciding it at release time.

This plan touches **only** package source and package tests. It deliberately does not touch
`main_market_data.py` so it can run in parallel with plan 27-01.
</objective>

<objective>
Close the one decode path in the whole repository that never passes through
`_request`: matriz's websocket daemon thread.

A newly started thread begins with an empty execution context, so the ContextVar
the rest of the phase relies on is simply absent there. Without an explicit
mechanism, every websocket frame would decode in observable mode regardless of
what the client asked for — a silent, mode-shaped hole in DEC-01.

Purpose: the phase's own concurrency criterion has two halves — no clobbering
between interleaved async tasks, and explicit propagation into the daemon
thread. Plan 05 proved the first half and proved the non-inheritance fact; this
plan acts on it.
Output: an explicit propagation helper in `ws_client.py` and a test file proving
both non-inheritance and propagation.
</objective>

First, settle the open assumption empirically before choosing a mechanism. In a
scratch script, measure what happens when a captured execution context is used
to run a callable more than once, and what happens when two such runs overlap.
Record the observed behaviour in the plan SUMMARY with the exact interpreter
version. The research flagged this as reasoned rather than executed, and the
choice of mechanism depends on the answer.

Then implement the mechanism. The recommended shape, which is re-entrancy-free
regardless of the measurement outcome: mirror the existing precedent in this same
file that hands main-thread token state to the daemon thread. Add a small named
private helper alongside it — one that takes the default REST client, reads
`default._state.strict_decode`, and stores it in a module-level snapshot. Call it
from `ws_connect` at the same place the token helper is called, before the thread
is constructed. Then, in the connection-open handler that already runs inside the
daemon thread, bind the snapshot into the ContextVar and open a decode scope, so
every frame the thread subsequently parses sees the mode. The daemon thread's
execution context is stable for its lifetime, so binding once at open is
sufficient and involves no context re-entry.

Give the helper a docstring citing D-04 in the same style the token helper cites
its own decision, and state the fact it exists for: a plain thread starts with an
empty execution context and does not inherit the caller's ContextVar values, and
the frame path never passes through `_request`, so there is no other place the
mode could arrive from.

Document the alternative mechanism — capturing an execution-context snapshot at
connect time and running the frame parser inside it — as a comment naming it as
the fallback and citing the measurement you just recorded.

Also harden the message handler so a decode raised in strict mode cannot kill the
connection loop for every subscriber: catch the package's decode error around the
frame parse, route it to the error callback if one is registered, and otherwise
log it through the package logger, then continue. Do not catch anything broader
than the package decode error — an unrelated exception must keep its existing
behaviour.

Reset the snapshot in `ws_disconnect` so a reconnection re-reads the flag from
the shared state rather than reusing a stale value.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| exchange websocket frames → `_parse_frame` | Untrusted streaming payloads decode on a background thread with no request context around them. |
| main thread state → daemon thread | The mode must cross a thread boundary that does not propagate execution context automatically. |
| daemon thread → every subscriber | An exception escaping the message handler tears down the connection loop for all subscribers at once. |

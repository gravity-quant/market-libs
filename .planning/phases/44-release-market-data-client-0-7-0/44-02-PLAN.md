<gate_authoring_deviation>
## Documented deviation from D-08's literal type enumeration — read before editing Task 2

`44-CONTEXT.md` D-08 requires each of the two gates to be authored literally as
`gate="blocking-human"` (never the bare `blocking` value) and enumerates two permitted task types:
`checkpoint:decision` and `checkpoint:human-verify`. **This plan honours the attribute requirement
exactly and deviates on the type**, authoring the gate as `checkpoint:human-action`. The deviation is
deliberate, is recorded here rather than made silently, and follows `44-RESEARCH.md` OQ-1
recommendation (a).

Why: `44-RESEARCH.md` § Gate Authoring Semantics measured the installed runtime instead of assuming
the attribute alone suffices, and found two independent auto-approval layers:

| Checkpoint type | Executor layer (`gsd-executor.md:314-318`) | Orchestrator layer (`execute-phase.md:1057-1061`) |
|---|---|---|
| `checkpoint:decision` | auto-selects the first option — **no gate-attribute exception clause exists at all** | auto-selects the first option, never reads the gate attribute |
| `checkpoint:human-verify` | honours `gate="blocking-human"` and refuses to self-approve | **auto-approves anyway**, never reads the gate attribute |
| `checkpoint:human-action` | "STOP normally" — always stops | "present to user" — always stops |

The string `blocking-human` never appears anywhere under `.claude/gsd-core/workflows/`; the
orchestrator is structurally unaware of the attribute. Additionally, `.planning/config.json` sets
`workflow.human_verify_mode: "end-of-phase"`, under which the planner is instructed to emit **no**
`checkpoint:human-verify` tasks at all — the gate would vanish rather than merely collapse.
`checkpoint:decision` and `checkpoint:human-action` are both explicitly exempt from that suppression.

Consequence: authoring this gate as either of D-08's two enumerated types — even spelled with the
correct attribute — would reproduce the exact defect this phase exists to eliminate, as its **sixth**
occurrence, while still passing a naive in-file grep. The measured census of prior defective
instances is five, not four: `34-02-PLAN.md:243`, `34-03-PLAN.md:168`, `40-01-PLAN.md:305`,
`40-02-PLAN.md:259` and `40-03-PLAN.md:172`.

What is preserved from D-08 verbatim: the attribute value `gate="blocking-human"` is present
literally in the task's opening tag (ROADMAP criterion 4 greps the plan file itself, not the observed
behaviour); the two gates live in two separate `autonomous: false` plan files; and the Phase-40 prose
armour is copied verbatim into the checkpoint action body as defence in depth, since that prose is what actually
saved the previous five occurrences via manual orchestrator override.

The post-hoc audit that closes ROADMAP criterion 4 runs in this plan's Task 1 verify block, before
anything irreversible happens, and again in `44-03` Task 3.
</gate_authoring_deviation>

<threat_model>
This phase adds five read-only, authenticated `GET` builders/parsers and five tolerant models to an existing client library. There is NO new auth flow, NO secret handling, NO mutation, NO new transport, and NO new dependency. The threat surface is honestly narrow.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client → market-data API | Authenticated GET crosses here; Bearer injection is handled by the UNCHANGED Phase-20 `_request`/`_ensure_token` layer (`authenticated=True` on the new specs is the only touch point) |
| market-data API → client | Untrusted/partial/hostile response payloads are parsed by `from_api` and the parser guards |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-22-01 | Information Disclosure | `endpoint_name` on the 5 builders + structured log records | accept | `endpoint_name` values are static literals (`instruments`, `segments`, `symbols`, `calendar`, `calendar_config`) with no user data; credential redaction is already enforced by the Phase-20 `RedactingFilter` (unchanged). Filter values (`q`, `prefix`) are not secrets. No new logging added. |
| T-22-02 | Tampering / DoS | `from_api` deserialization + the 5 parsers | mitigate | `SafeModel.from_api` never raises on partial/None/hostile payloads (substitutes typed zeros); collection parsers guard 204/null → `[]`; `parse_calendar_config_response` falls back to `from_api(None)`. Bounded blast radius; Phase 23 reconciles real shapes. |
| T-22-03 | Spoofing | `authenticated=True` on the 5 builders | mitigate | `authenticated=True` triggers the existing Bearer injection + `_ensure_token` in `_request` — no unauthenticated reference read reaches the API; no new auth code introduced. |
| T-22-SC | Tampering | npm/pip/cargo installs | accept | No new dependencies are added this phase (no install tasks); the supply-chain checkpoint does not apply. |
</threat_model>
